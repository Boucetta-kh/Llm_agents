In general terms with regard to file handling in databases like SQL Server (which handles binary Large OBjects), you're correct that large scale data management can be complicated due to issues such as performance, storage and locking contention for concurrent writes or reads accesses. However the advantages of each approach are:
1) LOAD_FILE(): This method is straightforward in handling files from a file system on your server (like local filesystem). It's simple enough that you can use this to store large images directly into SQL Server without needing an additional step like image resizing or conversion. However, if the uploaded content isn’t static and it varies based upon time/day etc., then loading in as BLOB will not be feasible since a row cannot have two different values for each column (data type).
2) `FILENAME`(): This function retrieves file names of files stored at specific locations on your server. It gives you the name, and it's much easier to use this method if there are multiple places where images need to be loaded from due its simplicity in getting only one location rather than a set list for each image load operation 
3) `STREAM_READ`(): This function allows reading of files stored at your server. It is useful when you want read large file chunks (e.g., multipart uploads), or if the data doesn't fit into memory then just to a very small portion from disk for later use, since SQL Server can only hold in-memory information and not entire content of files until they are all loaded at once by `STREAM_READ` method (this is similar as streaming large file).
4) BULK INSERT: This approach allows you upload data to the server directly from a CSV or TXT file, which can be much faster than loading each row individually. Also it supports bulk inserts of more rows in one go without any locking/wait mechanism and provides ability for concurrent writes (in case there are multiple users accessing your database at once).
5) Direct COPY: This function allows you to copy data from a CSV file or SQL Server table directly into another location on the server. It's usually faster than full-table loads as it operates in chunks, and can load much larger amounts of rows using only disk I/O rather then memory for storing intermediate results (this is more efficient).
6) FileStream: This function uses a file stream to read data from multiple files at once. It's very useful when you want the full content as per requirement but it could be slow due high CPU usage in case of large size datasets, because SQL Server needs additional time for processing all operations and returns only one result set (this is more efficient).
In conclusion: Depending on your specific use cases or requirements there are many ways to handle file data. Choose the method that best suits you as it will depend upon factors like speed/performance requirement of operation(s), storage constraints, how much CPU resources they require etc., not all methods have pros and cons in terms of both readability & simplicity (in some case) or performance impact if implemented correctly within your application design.
